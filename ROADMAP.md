# SpriteStudio Player for React Native — Player Roadmap

The **React Native Player** roadmap. It tracks React-Native-specific work for capabilities the Rust runtime exposes (`SpriteStudio-SDK/ROADMAP.md`). This file is **forward-looking only** — already-shipped features (the draw kinds Normal / Mesh / Shape / Instance / Effect, the framebuffer blend table, PartColor, mask and clipping, the thirteen `ss-*` integration shaders, the override layer, user-data / audio / signal events, the animation lifecycle, `fit`/`align` placement, the resource and atlas caches, `<SpriteStudioScene>`, the Expo config plugin and the typed asset manifest) are not repeated here.

[CONTRIBUTING.md](CONTRIBUTING.md) is the working guide and [README.md](README.md) carries the requirements.

Legend: ☐ **Ready** (Player-only, can start now) · 🚧 **In progress** · ⛔ **Blocked on the SDK** · 🕒 **Deferred**.

## Draw kinds and rendering

- ☐ **`Nines` and `Text`** — the two remaining kinds, and the two with **no reference port to read**: `SSWebGLRenderer` handles Normal / Mesh / Shape / Effect / Instance / Mask and names neither `DrawBatchKind.Text` nor `.Nines`, so this port would be first rather than catching up. Nines shares Shape's box-coord idea but has its own CSR buffers. Text is settled SDK-side as a **Player responsibility** (SDK ROADMAP, decided 2026-07): glyphs need host resources the Brain does not own — an outline font is named by family only and never ships in the `.ssab`, a bitmap font is rasterised at conversion time and does ship (`FontBitmap` / `FontGlyphBitmap`), leaving layout. The Brain still emits a **geometry-less `Text` batch per text part** so the part keeps its place in priority order, which is what a Player has to composite against; text authored as a mask is dropped from the plan instead, having no glyphs to write coverage with.
- ☐ **Masked Effect.** An effect draws unmasked: the coverage sample is placed per fragment, and an effect is a cloud of particle quads with no single shape to cut. Masked **Mesh** is now handled and left this list — the quad path inverts an affine UV to place the sample and the Shape path writes the coverage UV into its spare texcoord channel, but a mesh has neither (its one channel carries its atlas), so it is drawn into an isolated layer and the layer is cut by the coverage with `kDstIn` (`SsSkiaDraw.cpp`), the covering-texture form ForGodot and the wgpu coverage backend use. **SSPlayerForWeb clips masked Mesh** against the stencil (`SSWebGLRenderer`'s `isContentKind` is Normal / Mesh / Shape); this port now matches it, closing the one visible divergence. Masked Effect is unimplemented there too.
- ☐ **A caller's mask reaching *into* a child that also has its own writers — both coverages sampled by one part at once.** The one-way carry-over now ships: a mounted child's clipping writers are lifted up into the caller's coverage to clip the *caller's* parts drawn after the mount (`SsMaskPlan::bubbleChildClipWriters`, `HybridSsContext::prepareForBubble`), which `InstancePropagation` (from the WGPU test data, `Hole32` hidden) exercises. The other direction at the same time does not: when a caller's mask reaches *in*, the child references the caller's coverage and builds none of its own, so its own writers write nothing that frame. §5-2 says to handle them separately, and this port still runs one track. The three `MaskInstance` scenes hold the mask parts with the sub-animations unmasked internally, so nothing bundled in `example/` forces the two-track case.
- ☐ **The `ss-*` integration shaders, read in composition.** All thirteen have bodies and `pnpm run check-shader` pins each one, but it draws a flat quad through a single shader — what it cannot see is the effect with the atlas's real UVs, a PartColor riding along and a blend mode underneath. The neighbour-samplers are where that gap is widest: `ss-blur`, `ss-outline`, `ss-move` and `ss-scatter` step by texels, and a part whose cell is packed tight against its neighbours in the atlas will pull in whatever is next to it. SS6 and the other ports have the same property, so matching them may mean matching that too — worth reading on a screen before deciding it is a bug.
- ☐ **A batch of more than 65,535 vertices draws wrong.** `SsBaker` rebases each part onto its batch through a `uint16_t`, and `SkVertices` takes `uint16_t` indices, so the ceiling is the draw call's and not just the cast's — past it the geometry folds back on itself rather than failing. Nothing in `example/` comes near (Ringo peaks at 653, the heaviest effect at 620), so this is a limit to split batches on, not a bug anyone has seen.
- ☐ **Pixel tests.** "The modes differ from each other" is proven for the blends; "each mode is *right*" is not, and the same gap covers PartColor, Mesh, Effect and the integration shaders. SSPlayerForFlutter measures every blend row against the GL formula; there is no equivalent here.
- ☐ **`useSsPartTransform` runs its own frame loop, one per part** — and every `<SpriteStudioPartAnchor>` is one of it. Each hook instance starts a second `requestAnimationFrame` beside the view's, and reads through `getPartTransform(partName)` — a string across JSI, every frame, per part. It is the one consumer-facing API that reintroduces exactly the per-frame JS work the rest of the design removes. Reading by index, or publishing from the draw the view already runs, would both fix it; the second is the one that composes with the tick below.
- 🚧 **Reanimated tick.** Part transforms already publish as a SharedValue (`useSsPartTransform`), which is the consumer-facing half and the one that does not change when the tick moves. **What is left is the tick itself**: it is still `requestAnimationFrame` on the JS thread. `useFrameCallback` needs the whole update→bake→draw chain reachable from a worklet runtime, and the borrow rule says update and draw cannot land on different threads. SharedValues *in* — frame / speed / blend weight — are untouched; the blend-source and crossfade C-API they would drive (`ss_runtime_add_blend_source`, `ss_runtime_crossfade`) is already there and unbound.

## UI integration

This port starts ahead of its siblings here: a `<SpriteStudioView>` is a real native view, so Yoga already lays it out, and `fit` / `align` placement shipped. What is missing is everything past placement — the parts of a control the view does not implement. `Nines` and `Text` above are the drawing half of the same story.

- ☐ **Per-part hit testing.** The view answers pointers as a rectangle, so an irregular button eats every tap inside its bounding box and a transparent margin swallows whatever is behind it. Two pieces, in order: a **part rect read-out** built from the `PartState` fields the runtime already delivers every frame (`size_x` / `size_y`, `anchor`, `pivot`) plus the part transform — it belongs beside `getPartTransform`, and reading **by index** avoids repeating that hook's per-frame string marshalling — and then `hitTestPart(x, y)` over it, in view coordinates so the `fit` transform is already applied. The same read-out is what a caller needs to place a `<Pressable>` over one part of an animation.
- ☐ **UI state binding.** `<Pressable>` hands its child a state (`pressed`, and `hovered` / `focused` on the platforms that have them); nothing maps that onto an animation or a label, so every app writes the same `onPressIn` / `onPressOut` glue. A component that takes a state-to-animation map keeps it in one place, and is the only piece of this that is purely JS.
- ⛔ **Stretch a `Nines` part to the layout box.** The runtime evaluates a Nines part's size from its keyframes and hands over finished vertices, and the Override Layer covers colour / cell / visibility only — nothing can resize one from the host, so an authored window frame cannot follow the box Yoga gives it, and scaling the player distorts the border art rather than stretching the middle. Waits on the SDK **Per-part size override** (Phase 3) — the Override Layer extended with `size_x` / `size_y`.

## Platform and verification

- ☐ **A physical device.** Everything here has been seen on the iOS simulator and the Android emulator only — no device, on either platform. This is the one thing keeping the basic-playback exit criteria open.
- ☐ **Re-measure on a real device.** The simulator's host is an Apple Silicon Mac, so the CPU side — the side the JS-marshalling variants are limited by — is flattered relative to a phone.
- ☐ **The integration shaders, compared against another player.** They have now been read on the example's `Shader` card, with every effect visibly applied — that plus `pnpm run check-shader` (every body compiles, the uniforms line up, each port matches its neutral and characteristic case, `ss-sepia` matches SS6 to 1/255) is what stands behind them. What neither establishes is *fidelity*: nobody has put this card beside Godot's or the Web player's and compared frames, and several of these effects would look plausible while being subtly wrong. (`overall/Shader.ssab`'s "28 parts, all 13 ids" was never coverage: it comes out of the **bake plan**, which says what the pack asks for, not what drew.)
- ☐ **Nothing in this repository compiles the package's C++.** `tools/check-*.sh` links the host `libssruntime`, but what it compiles is its own `.cpp` — `cpp/` and `android/src` are built only by an iOS or Android build, so a change written almost entirely in C++ is verified by everything except a C++ compiler. A host syntax check is not the way round it: the generated Nitro specs include `<NitroModules/…>`, which resolves through CocoaPods' header map rather than through any include path a host `clang++` can be handed. What would close it is a CI job that runs the example's `expo prebuild` and builds one platform.
- 🕒 **macOS** — RN Skia and Nitro both support it, so it may simply work. Not in CI, not guaranteed.
- ⛔ **The pinned SDK release does not exist yet.** `scripts/SDK_VERSION.txt` names a tag the SpriteStudio-SDK repository has not published, so `pnpm run download-sdk` fails and `pnpm run release` fails with it — that is the correct failure, since there is nothing to publish against. Three things unblock together with it: the README can stop presenting `download-sdk` as the no-Rust path while it cannot work, `download-sdk` can say *why* a 404 is expected rather than printing curl's, and the submodule gitlink can move from a branch commit to the tag. **It gates every publish, prerelease included**, and not only through `release`: `prepack` refuses a tarball whose `native/BUILD_MODE` is not `release`, only `download-sdk` writes that file, and `build-runtime` deletes it on purpose — a local build is not the pinned release. So building the Brain from the submodule is not a way around this one.
- ⛔ **No ABI version symbol to check against.** `native/VERSION` and `SSPLAYER_SDK_VERSION` both describe what was *installed*, not what is linked, so a Player built against one Brain and linked against another has no way to notice. A `ss_runtime_abi_version()` would let every port compare once at startup. Not investigated beyond stating it.
- ⛔ **tvOS / visionOS** — blocked on the **Brain**, not on React Native: the Rust targets are Tier 3 and the SDK's XCFramework has no slices for them (an SDK ROADMAP item).
- ⛔ **Windows** — neither Nitro nor RN Skia supports react-native-windows, which is a separate C++/WinRT stack. No route.

## Distribution

- ☐ **What the first published version is called, and what promotes it.** Undecided, and worth settling before the SDK tag lands rather than after. Two facts to decide against. The family line is `7.0.0-beta.1` — the SDK tag `scripts/SDK_VERSION.txt` pins, and every `@spritestudio/ssplayer-*` package — while this Player is genuinely younger than that: no physical device has run it, `Nines` and `Text` are missing, and npm packaging is still undecided. So a first release numbered *below* the family line is honest rather than inconsistent, provided the README says the number describes this Player's maturity and not the SDK's; a prerelease also wants a dist-tag of its own rather than `latest`, which `publishConfig.tag` now sets to `beta`. The second fact is what should promote it: the two items actually holding the exit criteria open are the physical device above and the packaging decision below — **react-native-web is not one of them**, since it adds a platform rather than maturing this one, and it is deferred besides.
- ☐ **npm publishing.** The build half is settled on `react-native-builder-bob`: `main` / `module` / `types` resolve into `lib/`, `prepack` runs `bob build` ahead of the pack, and `react-native` / `source` stay on `src/` because Metro compiles the TypeScript itself. The packing half is settled too: `files` carries the Brain's static libraries (~57 MB unpacked, 16 MB on the wire), the vendored flatbuffers headers and the licences, and `prepack` refuses a tarball missing any of them — or built against a debug Brain, which `native/VERSION` cannot tell you about. The channel is wired: `.github/workflows/release.yml` dispatches `scripts/release.sh` on a macOS runner, defaulting to `--dry-run`, and `publishConfig.tag` is `beta` so a publish cannot take `latest` by accident. **One thing is still open:** `browser` (the web stub barrel) still points at `src/index.web.ts` rather than into `lib/`, which the field's own `//browser` note in `package.json` records.
- ☐ **Bare React Native support** — an app with no Expo config plugin gets neither the asset copy nor the ABI narrowing, so both build steps need documenting by hand and checking. `CMakeLists.txt` already tells "does not ship this slice" apart from "not installed" and names the `-P` escape.
- ☐ **React Native Directory listing** — `ios` and `android` up, in an entry appended to `react-native-libraries.json` (`react-native-community/directory`). It **cannot come before npm publishing**: the Directory reads the registry for its data and says so outright. Three things not to get wrong. **`false` values are skipped, never written**, so `web` and `expoGo` are stated by their *absence* — the web filter then excludes this package, which is the correct outcome and not something to work around; the prose belongs in the README, which carries it. **`newArchitecture` takes `'new-arch-only'`**, which is this port exactly — the field is otherwise auto-detected, and a failed detection reports "untested" rather than nothing. And **`alternatives` is not the place to point at SSPlayerForWeb**: it is for a library that is unmaintained or lacks New Architecture support, neither of which this is. (`configPlugin` is auto-detected, and true here.)
- ☐ **Documentation site — published.** The VitePress site is built and deployed by `.github/workflows/pages.yml`, in English and Japanese. What is left is the publish itself, which happens on the first release.
- ☐ **Example app beyond one screen** — the benchmark harness is gone and what is left is a single player; a real showcase is still owed.

## Surroundings

- 🕒 **react-native-web. Deprioritised 2026-08-21**, on a cost that is bounded: the stub barrel (`src/index.web.ts`) already keeps a mixed web/native app's web bundle *building*, so what is missing is the drawing and not the build — and the build is the failure that would actually cost an adoption. What the route adds is sharing the *component tree* between one app's two halves, which is narrower than "SpriteStudio on the web"; SSPlayerForWeb answers that completely, and a web-only ask belongs there. Blocked in fact besides — neither `@spritestudio/ssplayer-core` nor `@spritestudio/ssplayer-webgl` is published to npm (both 404). When it is revisited there are **two routes, and the cheaper one is not the better one.** Taking `@spritestudio/ssplayer-webgl` as-is shares **only the L3 API and L4 prop types**, and pays forever in keeping two renderers in agreement — the one disagreement that stood there, **masked Mesh**, has since closed (both clip it now; `SSWebGLRenderer`'s `isContentKind` includes Mesh, and this port's layer route matches it). Taking `@spritestudio/ssplayer-core` under **CanvasKit** instead shares **L2–L4 whole**: RN Skia runs on web, so the only layer web lacks is L1, and `ssplayer-core` is renderer-agnostic TypeScript — `GeometryBuilder` is "purely mathematical geometry operations", with `MaskPlanner`, `MaskComposition` and `PartTransform` beside it. More to write, and then two L1 implementations draw through one Skia API rather than two unrelated renderers. **Neither route vendors SSPlayerForWeb.** A submodule would hang a second `SpriteStudio-SDK/` gitlink in the tree to drift against the root one; and a vendored copy of a package the consumer may already have is the two-copies problem peer dependencies exist to prevent. **What has to match is the SDK ABI, not a git SHA** — an npm range says that, and both repositories pin `v7.0.0-beta.1` today. Keeping L2 React-free and L3 an interface is what leaves the door open; revisit on a concrete request.

## Backlog (small / optional)

- ☐ **Embedded audio bytes.** An `--embedded` pack carries its audio in `embedded_assets` with no sibling on disk, so `filePath` names nothing openable; the event's `embedded` flag keeps that legible rather than presenting as a missing file. The shape it wants is the texture one — a pack-level `getSounds()` read once at load, not an `ArrayBuffer` per event that the next `update()` invalidates.
- ☐ **`SsShaderEffect`'s compile cache is not thread-safe.** Function-local statics with no synchronisation, which is fine while every draw is on the JS thread and stops being fine the moment the tick moves to a worklet runtime. Worth doing *with* that move rather than before it, so the ordering rules are written once.
- ☐ **`pnpm run generate-assets` from the repository root does nothing useful.** It resolves `./assets/ss`, which only exists inside `example/`, so from the root it reports "no directory" and exits. Either point the script at the example or drop it and document the `npx` form.
- ☐ **`tools/check-framedata.sh` dies silently without Homebrew.** `FB_INCLUDE=$(brew --prefix …)` under `set -euo pipefail`, with stderr redirected, so a Linux host gets exit 127 and no output at all. It should say what it wanted.
- ⛔ **Free an embedded atlas after decoding.** The encoded bytes sit inside the same contiguous FlatBuffer the resource holds for its life, so embedded permanently costs one encoded atlas on top of the decoded texture. Needs an SDK-side way to drop `embedded_assets`, or a converter that emits a stripped companion.

## Deliberate non-goals

Each is this port's own decision, **not** "matching the Web / Flutter / Godot ports" — those disagree with each other and with this one.

- 🕒 **A recursion guard on Instance parts.** An instance part that mounts its own animation recurses until the stack gives out. Left as it is, and the general rule it comes from is worth stating once: **the safety code in this Player is kept to a minimum.** What a Player is for is simplicity and speed, and every defensive branch costs both. Which pack and which animation an app plays is the app's own business; a cyclic reference is a content bug its author can see in the editor. A depth cap decides on that author's behalf where legal nesting should have stopped, and cycle detection is more machinery than the case is worth.
- 🕒 **Validating what a caller passes to the transport.** `seek(NaN)` reaches `ss_runtime_set_frame_no` unexamined — NaN fails every comparison, so the Brain's clamp passes it through and the frame it produces has no parts in it. One `Number.isFinite` would stop it, and it is left out for the same reason as the recursion guard above: what an app asks the transport to do is the app's own business, and a Player earns its keep by being simple and fast rather than by checking its caller's arithmetic. Recorded because the symptom — everything vanishes — reads as a renderer fault rather than a bad argument.
- 🕒 **A per-frame callback (`frame_updated`).** The flagship emits one every tick, but it is a C++ signal inside an engine there and would be a JS-thread callback here — on the one path this design is built around avoiding, for every player on screen, every tick. The per-frame *value* case has a better answer in `useSsPartTransform`; the *reaching a frame* case is what the authored user-data and signal keys are for. Revisit on a concrete case that neither covers.
- 🕒 **`ss_runtime_set_frame_rate`** — on request only; it overrides the authored fps of the animation being played. Two things to know first: it belongs in `applySettings()`, because `setup_animation` resets `fps` the way it resets the loop count; and `ss_runtime_get_frame_rate` reports the **effective** fps, not the authored one.
- ⛔ **`ss_runtime_reset`** — not needed by this design. It empties a context, and a load here builds a **new** `SsInternalPlayer` whose context is created fresh and disposed with it. It becomes necessary only if a context is ever reused across packs, which would be traded against the exact `liveHandles` accounting the leak check stands on.
- 🕒 **A bundled converter.** React Native has no editor to host an importer in, so `.sspj` → `.ssab` stays a host-side `ssconverter-cli` step.
- 🕒 **`map0`/`map1` extra shader textures** — no asset here authors one, and they would need a second and third entry in the per-call texture table.
- 🕒 **Shader parts on Mesh / Shape / Effect kinds** — the reconstruction wants one affine quad to invert. Masking, which used to be excluded on the same ground, now reaches Mesh and Shape by other routes (a layer cut / a spare texcoord channel), so only Effect is still out of both. (Shader × *mask*, which this list used to doubt, does compose and is shipped.)
