# イベントとユーザーデータ

タイムライン上に作成されたキーはコールバックとして届きます。足音や当たりフレームは、
横で維持しているタイマーではなくアニメーション自身から発生します。

```tsx
<SpriteStudioView
  source={SsAssets['overall/UserData']}
  onUserData={(e) => console.log(e.partName, e.frameNo, e.integer)}
  onAudio={(e) => playAudioEvent(e)}
  onSignal={(e) => console.log(e.commandId, e.params)}
/>
```

3 つとも `partIndex`・`partName`・`frameNo` を持ちます。`frameNo` は**キーが置かれて
いるフレームであって、それに気づいたフレームではありません**。ユーザーデータのキーは
4 つの省略可能なスロットを持ち、それぞれに `has…` フラグが付きます — `integer`、
`pointX`/`pointY`、`rect`、`text` です。まずフラグを読んでください。フラグが false の
ときの値は「作成された 0」ではなく、単にゼロ相当の何かです。

いずれも**読み取りであって、取り出しではありません**。ランタイムは収集のたびにリストを
組み直すので、1 ティック中に 2 回呼んでも同じイベントが返り、一度も呼ばなくても何も
失われません。

ハンドラは対応する prop がある間だけ設定されます。毎フレームの読み取りがその有無で
制御されているためです。インラインのアロー関数を渡しても問題ありません — ロードを
やり直したりはしません。

## オーディオは通知されるだけで、再生はされません {#audio-is-reported-not-played}

`onAudio` は*何を*・何回・どのファイルを再生すべきかを伝えます。再生はしません。
React Native には標準のオーディオ API がなく、パッケージ側でライブラリを 1 つ選んで
しまうと、音を一切使わないプロジェクトにまでそれを背負わせることになります。

参照実装はサンプルアプリの `src/player/audio.ts` です。自分で書く人が必ずぶつかる
3 点を解決しています — `asset` スキームの兄弟ファイルにはオーディオライブラリが開ける
パスが無いこと、`loop_num` は多くの API がブール値を取るところで*回数*であること、
そして iOS は `setAudioModeAsync({ playsInSilentMode: true })` が無いとサイレント
スイッチで無音になることです。

## ライフサイクル

`onAnimationStart`・`onAnimationChange`・`onLoop`・`onComplete` はいずれもアニメーション名
を運びます。1 つのプレイヤーは、その上に載るアニメーションより長生きするからです。

知っておく価値のある挙動が 2 つあります。**start は再開では発火しません**（`playing` が
false → true になったときは、やり直しではなく継続します）。そして**change は同じ
アニメーションのやり直しでは発火しません** — それは start として報告されます。

::: warning ハンドラ内の例外はクロックを止めます
これらが配送されるのは `advance()` の中で、それはフレームループの中で走ります。つまり
あなたのハンドラからの throw はアニメーションを止めます — シーンの中であれば、その
すべてのスプライトを止めます。これは意図的です。その例外はあなたのものであり、ここで
握りつぶされるのではなく、あなたのエラー処理へ届きます。
:::
